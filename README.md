# AI Budget Book — AI 자동 가계부 (Android)

**결제 알림을 읽어 가계부를 자동으로 작성하는 개인용 Android 앱.**

가계부 앱이 실패하는 이유는 기능이 부족해서가 아니라 **사람이 매번 입력해야 하기 때문**이다.
이 앱은 사용자가 입력하지 않는다. 카드사·은행 앱이 띄우는 결제 알림을 읽어
금액·가맹점·카드·시각을 뽑아 저장하고, 사용자는 통계만 본다.

```
카드로 결제  →  알림  →  파싱  →  분류  →  SQLite  →  통계
                                    ↑
                        사용자는 여기까지 아무것도 하지 않는다
```

> **모든 데이터는 기기 안에만 저장된다.** 서버 없음, 계정 없음, 동기화 없음.

## 주요 기능

### 🔔 자동 기록
결제 알림을 가로채 금액·가맹점·카드·시각·할부를 뽑아 저장한다.
앱이 백그라운드에서 종료돼도 네이티브 파일 큐에 쌓여 **유실되지 않는다.**

### 🏷 브랜드 학습
처음 보는 브랜드만 **한 번** 고르면 이후 자동 분류된다.
브랜드 규칙으로 승격되므로 아직 본 적 없는 지점(`메가커피 강남점`)까지 커버한다.

### 💰 수입 / 지출 / 순증가 분리
수입과 지출을 절대 합산하지 않는다. 같은 날짜 안에서도 지출·수입을 그룹화해 보여 준다.

### 🏦 자산 자동 반영
결제하면 계좌 잔액이 자동으로 줄어든다. 잔액은 저장값이 아니라
`기준 잔액 + 기준 시각 이후 거래 합` 으로 **계산**하므로 어긋날 수 없다.

### 🧾 더치페이 정산
30,000원 결제 + 20,000원 정산 = 통계에 **10,000원**.
원본 거래 금액은 절대 고치지 않아 카드 명세와 항상 대조할 수 있다.

### 🔁 정기결제 자동 감지
같은 브랜드가 일정 주기로 3회 이상 비슷한 금액이면 후보로 제안한다.

### 📊 통계
소비(카테고리/브랜드/추이) · 수입(카테고리/월별) · **소비 / 저축 / 청약 / 투자 분리** ·
프로젝트별 · 요일 패턴 · 브랜드 드릴다운.

### 🤖 AI 분류 (선택, 기본 꺼짐)
**실시간 AI 호출이 없다.** 분류하지 못한 거래는 대기열에 쌓아 두고,
노트북에서 Ollama 가 켜졌을 때 **브랜드당 한 번씩** 몰아서 처리한다.

### 🧠 사실 기반 분석
"배달 +82,000원이 가장 큰 원인", "금요일 술값 평균 42,000원",
"주 2회 줄이면 월 36,000원 절약" — **모든 숫자는 코드가 계산한다.** LLM 은 문장만 만든다.

## Ollama 연결 (선택)

AI 는 **필수가 아니다.** 꺼져 있어도 모든 기능이 동작하고,
처음 보는 브랜드만 사용자가 한 번 고르면 된다.

### 노트북에서

```bash
# 외부 접속 허용으로 띄운다(실기기에서 접속하려면 필요)
# Windows PowerShell
$env:OLLAMA_HOST="0.0.0.0:11434"; ollama serve

# 모델 설치
ollama pull gemma3:4b
```

4B 급 모델을 쓰는 이유: 이 작업은 "가맹점 이름 → 업종 분류" 라는 좁은 분류 문제다.
큰 모델이 필요 없고 CPU 로도 수 초 안에 답한다.

**어떤 모델이든 설정에서 바꿔 쓸 수 있다.** 추론(thinking) 모델을 넣으면
앱이 요청 형태를 자동으로 맞춘다 — 일반 모델에 `think` 필드를 보내면
최신 Ollama 가 "does not support thinking" 으로 요청을 거절하기 때문이다.

| 모델 | 요청 |
|---|---|
| `gemma3:4b`, `llama3.2:3b`, `mistral` | `think` 미전송 |
| `qwen3:4b`, `deepseek-r1` | `think: false` + 프롬프트에 `/no_think` |

### 앱에서

| 실행 환경 | Ollama 주소 |
|---|---|
| Android 에뮬레이터 | `http://10.0.2.2:11434` (기본값) |
| 실제 기기 (같은 Wi-Fi) | `http://<PC의 LAN IP>:11434` |

1. 설정 → **Ollama 주소** 입력
2. 설정 → **모델** 입력 (`gemma3:4b`)
3. 설정 → **연결 테스트** — 서버와 모델 설치 여부를 함께 확인
4. 설정 → **AI 자동 분류 사용** 켜기
5. 대시보드에 `AI 분석 대기 N건 [지금 분석]` 배너가 나타난다

> PC 방화벽에서 11434 포트 인바운드를 허용해야 할 수 있다.

### 노트북이 꺼져 있으면?

아무 문제 없다. 대기열이 쌓이고 배너는 나타나지 않는다.
거래 기록·통계·검색·수정은 전부 정상 동작한다.

## 카카오 API 설정 (선택)

브랜드 이름으로 장소를 검색해 **업종**을 알아낸다.

```
"동네작은카페" → 카카오 → "음식점 > 카페 > 커피전문점" → 식비/카페
```

### 발급

`developers.kakao.com` → 내 애플리케이션 → 앱 키 → **REST API 키**
앱 → 설정 → **카카오 REST API 키** 입력 → **키 확인**

### 비용이 발생하지 않는 구조

| 장치 | 내용 |
|---|---|
| 무료 API | 카카오 로컬 API 는 무료이고 카드 등록이 필요 없다 |
| **사용자 본인 키** | 앱에 개발자 키를 심지 않는다. 심으면 추출되어 오용되고 할당량이 공유된다 |
| 브랜드당 1회 | 캐시 우선. 같은 브랜드를 두 번 조회하지 않는다 |
| 후보 5개를 1회에 | 호출은 1회인데 판단 근거는 5배가 된다 |
| **실패도 캐시** | 없으면 못 찾는 브랜드를 결제마다 재조회해 할당량이 사라진다 |
| 429 자동 중단 | 한도 초과 시 **24시간 자동으로 쉰다** |
| 키 없으면 비활성 | 기능이 그냥 꺼진 상태로 동작한다 |

### 보내는 것 / 보내지 않는 것

- ✅ 보냄: **브랜드 이름만**
- ❌ 안 보냄: 금액 · 카드 · 날짜 · **이체 상대방 이름**

GPS 를 쓰지 않는다. 백화점·푸드코트·역사에서는 한 좌표에 수십 개 가게가 있어
좌표보다 이름이 정확하고, 위치 권한도 요구하지 않는다.

### 후보 다수결 — 한 건만 믿지 않는다

한 건만 받아 확정하면 `본가` 처럼 이름이 흔한 가게에서 엉뚱한 분류가 그대로 굳는다.
그래서 **후보 5개를 한 번의 호출로 받아** 업종이 일치하는지 본다.

```
한식 한식 한식        → 한식 (만장일치)      → 자동 분류
한식 한식 한식 중식   → 한식 (다수)          → 자동 분류
카페 병원 약국 세탁소 → 판단 불가            → AI 대기열
한식 한식 중식 중식   → 동점, 판단 불가      → AI 대기열
```

**API 호출 횟수는 늘어나지 않는다.** 응답에 몇 건을 담을지만 달라진다.
판단하지 못한 것도 캐시하므로 재조회로 할당량을 쓰지 않는다.

LLM 은 최후의 수단이다. 앱이 충분히 판단할 수 있으면 Ollama 를 부르지 않는다.

## AI 분류 파이프라인

```
결제 알림
   ↓
① 사용자 규칙 / 학습된 가맹점        ← DB, 즉시
   ↓
② 내장 브랜드 사전                   ← DB, 즉시
   ↓
③ 카카오 장소 API (브랜드당 1회)     ← 선택, 캐시 우선
   ↓ 성공 → 저장 · 끝
   ↓ 실패
④ AI Pending Queue (ai_status = 'pending')
   ↓   ← 저장은 여기서 끝난다. 거래는 이미 기록되어 통계에 들어간다
   ─────── 나중에, 노트북이 켜졌을 때 ───────
   ↓
⑤ Ollama 연결 확인 → 브랜드로 묶기 → 캐시 확인 → (없으면) LLM 1회
   ↓
   brand_metadata 갱신 + 가맹점 학습 + 브랜드 규칙 승격
   ↓
   같은 브랜드 거래 전체 갱신 · pending 해제
   ↓
⑥ 그래도 못 하면 사용자 직접 선택
```

**위쪽에서 해결되면 아래는 호출하지 않는다.**

### 왜 실시간 AI 를 없앴나

결제 순간에 Ollama 를 호출하면:

1. 노트북이 꺼져 있으면 매 결제마다 타임아웃(최대 25초)을 기다린다
2. 그 시간 동안 알림 처리가 막히고 배터리를 쓴다
3. 밖에서는 Ollama 가 거의 항상 꺼져 있다 — **대부분의 경우 헛수고**

그래서 저장과 AI 를 분리했다. `행복반점` 을 15번 결제해도 **AI 호출은 1회**다.
브랜드 캐시가 쌓일수록 호출량은 계속 줄어든다.

## 설계에서 중요한 결정 3가지

### 1. 계산 가능한 값은 저장하지 않는다

계좌 잔액, 실제 부담 금액, 순증가는 모두 파생값이다.
저장하면 **어긋난 상태**가 만들어질 수 있고 사용자는 그것을 알 수 없다.
파생값이면 거래를 지우면 잔액이 자동으로 되돌아온다.

### 2. 이체 거래명은 브랜드로 학습하지 않는다

같은 사람에게 보내는 돈의 **목적은 매번 바뀐다.**

```
홍길동   오늘: 카페값   내일: 여행 경비   다음 주: 회비
```

`000 스마트폰 → 메가커피` 를 규칙으로 저장하면 이후 그 상대방에게 보내는
**모든 송금이 메가커피로 분류된다.**

판단은 한 곳에만 있다 — `brand_learning_policy.dart`.
자동 수집·사용자 수정·외부 API 전송·AI 일괄 분석 **네 경로 모두** 이 정책을 통과한다.

### 3. 숫자는 앱이, 문장만 LLM

> "메가커피 22회 → 주 2회 줄이면 월 36,000원 절약"

`36,000원` 은 `4,000원 × 9회` 라는 산수다. LLM 이 계산하면 틀리고,
사용자는 그 숫자를 믿고 돈 쓰는 결정을 한다.
**모든 금액·횟수·증감·절약액은 코드가 계산하고 테스트로 고정한다.**

|---|---|
| 높음 | **백업 / 복원** (앱 삭제로 데이터를 잃는 일을 막는다) |

## 개발

```powershell
flutter analyze                  # 무경고 상태를 유지한다
flutter test                     # 340개
flutter test test/database_smoke_test.dart
flutter build apk --debug
```

### 테스트 방식

이 프로젝트에서 특히 중요한 것들:

- **집계 SQL 은 실제 SQLite 로 돌린다** (`sqflite_common_ffi`). 손으로 쓴 SQL 이 많다
- **외부 API 는 호출 횟수를 센다.** "동작한다" 만으로는 할당량 낭비를 잡을 수 없다
- **개인정보 유출은 보낸 쿼리를 기록해 검증한다**
- **대조군을 함께 둔다.** "월급은 정기결제 후보가 아니다" 가 감지기가 아무것도 못 찾아서 통과하는 게 아님을 확인해야 한다
- **버그 수정 테스트는 수정을 되돌려 실패를 확인한다**
- 위젯 테스트에서 DB 는 `tester.runAsync` 안에서 (FakeAsync 존에서 실제 I/O 를 await 하면 멈춘다)

### 스키마를 바꿀 때

1. `db_schema.dart` 의 `databaseVersion` 을 올린다
2. `migrations` 맵에 항목을 추가한다 — `IF NOT EXISTS` / `ADD COLUMN` 형태로 **두 번 실행해도 안전하게**
3. 마이그레이션 테스트를 추가한다

### 네이티브를 바꿀 때

`flutter test` 는 Kotlin 을 컴파일하지 않는다. 반드시 `flutter build apk --debug` 로 확인한다.
